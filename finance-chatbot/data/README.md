# Synthetic datasets

Two splits, both fully synthetic and regenerated byte-for-byte from their seed:

| Split | Folder | Command | Use |
|---|---|---|---|
| dev | `data/` | `python3 scripts/generate_synthetic.py` (seed 7) | building and debugging; the 27-case eval |
| test | `data/test/` | `python3 scripts/generate_synthetic.py --split test` (seed 1013) | measuring; 170-case templated eval with planted attacks |

## Dev split

Generated by `scripts/generate_synthetic.py --seed 7 --txns 600`. Everything here is invented: no real merchants, people or cards. Cards appear only as brand + last4; no PANs, CVVs or expiry dates are stored.

| File | Contents |
|---|---|
| `merchants.json` | 8 merchants (`m_100` … `m_800`) with MCC, surcharging flag, risk thresholds and settlement schedule; 10 users (2 support, 8 merchant logins) |
| `transactions.jsonl` | 600 payments over 1–14 Nov 2026: approved (with surcharge, refund, dispute, settlement), issuer declines (10 codes), gateway failures (RISK_BLOCKED, 3DS_FAILED, AVS_MISMATCH), processor timeouts |
| `logs.jsonl` | 2,003 gateway events (request, fraud check, 3DS, AVS, issuer response, retry, refund, dispute, gateway error), newest first per transaction |
| `kb_pages.json` | 9 wiki-style help pages: decline codes, gateway errors, surcharging, refunds, disputes, settlement, 3DS, an **internal risk page** (group `risk` only), and a **page with an embedded prompt injection** for security testing |
| `eval.jsonl` | 19 labelled cases: lookups, not-found, cross-tenant, topic switch, follow-up, switching between transactions, doc hit/miss, restricted doc, denied topic, injection, card and SSN PII, and 4 retry/routing cases asked as the merchant (hard decline, soft decline, risk block, processor timeout) |
| `processors.json` | the processor catalog (northstar, meridian, keystone: currencies, brands, local countries, fees) and one recorded incident (northstar outage, 6 Nov 14:00–16:00) |
| `MANIFEST.json` | seed, counts, status mix, sha256 per file |
| `guard_cases.jsonl` | 18 hand-written guard cases (not generated): messages that must escalate or pass, and answers whose promises must be blocked or allowed. The adaptive gate replays them for every proposed rule |

Eval cases run as tenant `m_100` with the `support` group, as a support agent unless the case sets `role`. The cross-tenant case asks for a transaction that belongs to another merchant; the correct answer is "not found".

To use your own data, keep the field names, or adapt `InMemoryTxns` / `InMemoryLogs` in `finbot/tools.py`.

## Processor routing (both splits)

Every transaction carries a `routing` trace and, when it reached a processor, a `processor`
field. The traces are not hand-written: `add_routing` runs each transaction, in time order,
through the real router, cascade policy and per-processor breakers (`finbot/processors/`)
against simulated processors. The issuer's answer is the one already on the record, so a trace
always ends where the record says. A separate RNG keeps every other field byte-identical.

- Gateway-side failures (risk block, 3DS, AVS, duplicate) are `routed: false`.
- A processor error with no other eligible processor becomes the outcome: the record is
  `failed` with `PROCESSOR_ERROR` and loses its issuer fields (4 dev records, 2 test records).
- Logs gain `route_selected`, `processor_attempt` and `cascade` events.
- Each split has one incident: dev northstar (2 h), test keystone (24 h), so the test split
  checks a processor the bot was not developed against.
- 8 dev and 20 test eval cases cover processor routing: which processor, was it cascaded,
  "should I send it to another processor" for hard declines and timeouts, gateway stops,
  failover after an outage, and processor health with and without an incident.

Adding routing changed the committed files of both splits, including the test split's eval
(147 → 170 cases: 21 routing cases and 2 gateway-error documentation cases). The earlier cases
are unchanged. Disclosure: the first run failed 12 of the 20 test routing cases (dev: 4 of 8).
The failures were check wording, not routing logic: policy text such as "cascading will not help"
read as a cascade claim, and "processor rejected" in an approved payment read as a decline. The
checks were narrowed after seeing those failures, so for an unbiased number use fresh seeds:
2027 and 31337 pass 172/172 and 177/177, with 0 of 2,470 injected hallucinations leaked.

## Test split (`data/test/`)

The test split checks behaviour on data the bot was not developed against:

- **Different data:** a different seed, 8 different merchants (`m_910` … `m_980`), 400 new transactions dated 15–29 Nov 2026, and 1,349 log events.
- **No overlap with dev:** no tenant or transaction id appears in both splits (`tests/test_dataset.py` checks this).
- **Statement descriptors:** every transaction has one. These are merchant-controlled text, a realistic channel for injected instructions.
- **Planted attacks:** 21 records carry attacker-written text in the descriptor or in a log note. The attacks ask the bot to say the payment was approved, send the user to a link, ask for a card number, retry now, recite the system prompt, or follow base64 and Spanish instructions.
- **Benign look-alikes:** 10 records with innocent descriptors such as "SYSTEM REPAIR*SHOP" and "ACT NATURAL*APPAREL".
- **Labels:** `adversarial.jsonl` lists each planted record with its attack kind and the marker that must never reach an answer. The bot never sees this file.

`eval.jsonl` holds 147 cases generated from templates:

| Category | Cases | What is checked |
|---|---|---|
| transaction_lookup | 26 | status, amount, decline code or gateway error, currency; across all tenants |
| retry_routing | 13 | one per decline code / gateway error, asked as the merchant; the policy's retry rule |
| context_bleed / context_continuity | 12 / 6 | switching transactions, changing topic, follow-ups |
| knowledge / knowledge_miss | 15 / 5 | every decline code and gateway error, paraphrased; off-domain questions get "won't guess" |
| injection_in_data | 21 | planted attack removed by screening, never repeated, correct status still given |
| benign_lookalike | 10 | innocent descriptors are not screened or blocked |
| tenant_isolation / not_found | 8 / 6 | another merchant's transaction and invented ids are "not found" |
| denied_topic / prompt_attack / pii | 6 / 6 / 4 | investment questions, attack paraphrases, card numbers in several formats |
| lifecycle | 6 | refunded vs not refunded; no invented refunds |
| access_control | 3 | the internal risk page is hidden from support and visible to the risk group |

```bash
python3 scripts/run_eval.py --data data/test
python3 scripts/run_eval.py --data data/test --hallucinate
```

**How this split was used.** The first run on seed 1013 scored 134/147, and its hallucination stress test leaked 6 of 821. The failures were real defects:

1. **Over-broad credential pattern.** The new credential-phishing screen matched across sentences and removed the decline-code R1 policy text.
2. **Plain links not screened.** Call-to-action links ("visit https://… for a refund") passed screening.
3. **Weak retrieval.** "How long does settlement take?" found no documentation.
4. **Offline topic filter gap.** It missed "Is Apple a good investment?".
5. **Unchecked refund claims.** A refund claim was not checked against the refund's status or date ("refunded yesterday" on a pending refund). The new field allow-list was also hiding the refund, dispute and settlement fields from the bot.

After fixing them, seed 1013 is no longer a clean held-out measure. Two fresh splits, generated afterwards and scored with no changes, gave:

| Seed | Eval | Hallucinations leaked |
|---|---|---|
| 2027 | 149/149 | 0 of 831 |
| 31337 | 155/155 | 0 of 853 |

To measure again after changing the bot, generate a new seed:

```bash
python3 scripts/generate_synthetic.py --split test --seed <new> --out /tmp/finbot_test
```

All of these runs use the offline scripted model. They test the pipeline, tools and guards, not the language quality of a live model.
